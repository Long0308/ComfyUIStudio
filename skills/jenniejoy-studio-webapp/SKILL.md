## Explicit subskill contract

- **Input Trigger:** Completion of any real generation or review boundary (image candidate, dialogue WAV, H3 video clip, SeedVR2 upscale, or Remotion Master render).
- **Responsible Owner:** The live root or dedicated app-agent ID recorded in the film PLAN. “Studio Publisher” is the role, not its runtime identity.
- **Concrete Output:** Persisted registration in episode `studio-state.json`, verified media link via `/api/film-media/<film>/<artifact>`, truthful runtime ID when available (null for reuse/imagegen without one), requested and resolved model fields, verified SHA256 hash, and independent UI readback at `http://127.0.0.1:5050/films.html`. Episode-04 candidate/pilot media is published with `production-local/JennieJoyKids-Story/04-milk-and-mom/tools/publish_motion_v005.py` (additive edit of `production-local/JennieJoyKids-Story/film-library.json`, then `GET /api/films` readback; receipt in `technical/studio-publish-v005/`).
- **Downstream Result Consumer:** Reviewers, directors, and external clients inspecting production progress and playing back verified candidate media.

File creation on disk alone does NOT constitute production delivery. Every asset needs truthful provenance and a verified hash. ComfyUI jobs retain their genuine prompt/job ID. Reused assets and imagegen calls without a provider runtime ID use `runtime_id: null` plus source/tool provenance; never fabricate an ID or substitute a content hash for one. Keep requested image model separate from observed/resolved model.

### Persistent output preview protocol (Case 03 fix)
ComfyUI `SaveImage` nodes do not retain an in-graph buffer across web UI reloads or server restarts. Record these independent proofs, without inferring one from another:
1. **Comfy GUI proof:** Preserve `SaveImage`; resolve the helper under the active episode (`<episode>/tools/attach_comfy_result_preview.py`, not a root-level universal path). Copy the output into ComfyUI input and append a pinned `LoadImage` node, then reopen that specific workflow and save the result.
2. **Studio registration proof:** Register the asset in the supported Studio API/state with status, source path, hash, requested/resolved model and runtime ID (nullable as above). A GUI review workflow is not a Studio job.
3. **HTTP proof:** Read back the actual scoped media/API response, byte/hash availability and job/artifact status. Workflow JSON alone proves neither ingestion nor serving.
4. **UI proof:** Reopen `http://127.0.0.1:5050/films.html`, locate the specific film/artifact and verify image display or video playback. Save the timestamped readback.

Do not promise that adding `LoadImage` automatically publishes a preview to `/films.html`.

## "Duyệt phim" review page (T-W02, `review.html`)

- Open `http://127.0.0.1:5050/review.html` (links in the Studio header and `/films.html`). Light theme only; the review cut is always labelled from RECEIPT (`REVIEW 1080p · native upscaled`), never 4K.
- GET-only, episode-scoped (`?episode_id=` or `X-Episode-Id`; unknown episode = 404): `/api/review/versions`, `/api/review/<vNNN>/{receipt,events,media,feedback}`, `/api/review/<vNNN>/boundary/<name>` (boundaries/ then stills/), `/api/review/<vNNN>/icon/<png>`, `/api/timing/words`, `/api/production/4k-status`, `/api/master/readiness`. Logic lives in `review_api.py` (path containment, Range via the shared `send_media`). A review folder without RECEIPT/mp4 yet is listed as "đang dựng" and is never the default.
- The only write: `POST /api/review/<vNNN>/feedback` `{decision: approve|changes, reviewer, comments:[{frame,text}], sha256, gate_verdicts?, confirm: "<decision>:<vNNN>"}` appends one JSON line to `editorial/review-feedback/review-feedback-<vNNN>.jsonl` (append-only; review/word-timing/technical/master trees are never written). `sha256` (the RECEIPT hash the page was loaded with) is REQUIRED; the server hashes the mp4 that RECEIPT names through one open handle (refusing a file that changed or was swapped while hashed) and answers 409 unless measured == RECEIPT == client (compared lowercase). The measured hash is stored as `video_sha256`. There is no fallback to "some other mp4": a folder whose RECEIPT-named file is missing is listed as unfinished and is never the default. JSONL files are split on the newline byte only (U+2028/U+2029/U+0085 inside a comment are data), unreadable lines are counted and shown by the page. Gate rows show builder evidence only; the critic verdict stays in PLAN.md. The page rejects empty or non-integer frame inputs before POST.
- `/api/production/4k-status` counts `runs/**/job.json` + `run-state.json` (no PID). Pace = mean completion gap of the last 10 chunks since the latest resume, after dropping gaps over 3x the median (idle pauses). `state: stale` means no job activity for max(15 min, 5 x s/chunk), i.e. the run is probably dead and root must resume it.
- `/api/episodes` returns `domain`, `updated_at`, `default_id` (most recent JennieJoy episode; NEWTECONS stays selectable, never the default). Invalid POST JSON answers 400.
- Colours (`test_ui_palette.py`): ONE Blue Web palette for every page, the main Studio page included. The user's palette (paper `#F7FAFD`, background `#FFFFFF`, ink `#0A2540`, muted ink `#5C6795`, accent `#0B4FD9`, horizontal pipe `#5B9BF5`, vertical pipe `#9D9BF5`, tag `#96E072` / `#134611`, bad `#D00000`, good `#3E8914`) plus tints that are exact blends of those over white (bases x alphas are computed in the test; there is no allow-list of stray tokens). Covered files: `index.html`, `app.css`, `app.js`, `review.*`, `films.*`, `voice-library.*`; every hex (3 or 6 digits) and every `rgb()` / `rgba()` triple must be a palette colour or tint, any other colour form is a violation (space-syntax `rgb()`, percentages, `hsl` / `hwb` / `lab` / `lch` / `oklab` / `oklch` / `color()` / `color-mix()` / `light-dark()`, and CSS colour names except `white` / `transparent` / `currentcolor`); the audit has negative controls for each form. The old pink / purple / indigo / emerald / sky / slate values were mapped by hue family and lightness (pinks, purples, sky, indigo to accent and its tints; greens to good / tag; reds to bad; slates to muted and its tints; near-black to ink). The same files are also emoji-free; `--primary-pink` became `--primary-accent: #0B4FD9`. Vocabulary icons are NOT edited in the stored data: `app.js` `VOCAB_ICONS` maps the stored emoji (written as `\u{...}` escapes) to a label and renders an inline Blue Web glyph (circle with the label's initial); the icon field is a select whose option values are the stored emoji and a legacy value outside the list is kept as "Giữ nguyên icon cũ".

## Job journal and 409 recovery (`job_journal.py`, `engine.py`)

What the code does, and where its limit is.

- ONE append-only journal per episode, `job-journal.jsonl`, for every long-running external job: ComfyUI prompts (`render_jobs`) and ffmpeg/node renders (`finishing_jobs`, every Popen). Each job writes `intent` (BEFORE the call: client job id + payload), `started` (prompt_id or pid) and `terminal` (final status). `seq` grows by one per record; the ComfyUI prompt carries `extra_data.studio_job_id` and saves to `episodes/<ep>/shots/<shot>/<job_id>/...` (job-specific output folder). Readers split on the newline byte only.
- COMPACTION MOVES FINISHED JOBS OUT OF THE LIVE FILE IMMEDIATELY: on every `Studio.save`, jobs whose terminal record is <= `journal_seq` go to `job-journal.archive-<UTC date>.jsonl` (append-only per day, same directory); live jobs stay and a `checkpoint` record takes the next seq number so no seq is reused. To audit a job, read the live journal AND every `job-journal.archive-*.jsonl`. A journal with unreadable lines is never rewritten.
- `studio-state.json` stores `journal_seq` = the last record the state reflects. Startup and a 409 reload replay only records with `seq > journal_seq`. A replayed job becomes current only when the slot is empty or the current job has a KNOWN smaller `journal_seq`. A current job of unknown provenance is never displaced: the journal job is PARKED instead. A journal that predates the `journal_seq` field is treated as already reflected. Superseded jobs are never resurrected; terminal jobs missing from the state are not re-attached.
- A live journal job is never silently dropped. When the slot is taken it is parked as a `render_job_history` entry with status `RECOVERY_REQUIRED` (a job with no prompt id, see reconciliation below, is a `RECOVERY_REQUIRED` current/parked entry with `prompt_id: null`). Such a job blocks `dispatch` for that shot (409).
- HOW AN OPERATOR CLEARS A STUCK / PARKED / FORGOTTEN JOB (no terminal needed): Studio step 4.3 has the button "Giải phóng tác vụ treo". It calls `GET /api/jobs/live` (journal-live ComfyUI jobs: shot, prompt id, status, `parked`, output folder `episodes/<ep>/shots/<shot>/<job_id>`, the files in it, and what ComfyUI says about the job: `comfy_state` listed / absent / unknown, `comfy_where`, `comfy_prompt_id`, `in_comfy_queue` true / false / null; the dialog shows "không kiểm được ComfyUI" for unknown and "đang gửi, chờ" for a young intent; rows also carry `in_flight` and `age_seconds`), asks for the resolution (`ABANDONED` = discard its output, `SUPERSEDED` = replaced by another run) and a browser confirmation, then `POST /api/jobs/release {job_id, resolution, confirm: "release:<job_id>", acknowledge?: "acknowledge:<job_id>"}` and journals `terminal` with `by: operator`; the slot is free and the same configuration can be dispatched again. A no-prompt-id open intent younger than `intent_grace` (120 s) is refused first (409 `in_flight`, "đang gửi, chờ <n> s"; no acknowledge overrides it) because its POST may still be in flight and ComfyUI may accept it late. After that EVERY job is looked up in ComfyUI (`/queue`; for a job without a prompt id also the whole `/history`, by the `studio_job_id` tag, and its output folder), and the hard rules are checked a SECOND time with a fresh read immediately before the terminal record is written: (1) listed in the queue = 409, wait or cancel it in ComfyUI; (2) an open intent / job without a prompt id that ComfyUI has (queue or history) = 409 AND the prompt id is attached from the tag (adopted as started), so nothing is posted twice; after it finishes it can be released; (3) ComfyUI cannot be asked: a job WITHOUT a prompt id (open intent), and a job whose prompt id was adopted from the tag (journal `reconciled`), are never released, not even with acknowledge (409 "Không kiểm được ComfyUI"); only a job whose prompt id Studio itself received from ComfyUI's answer needs the second confirmation (409 `needs_acknowledge`, the page asks again, then resends with `acknowledge`) and the response carries a `warning` that ComfyUI did not answer; (4) not listed but its output folder already has files: `needs_acknowledge` ONLY for a job without a prompt id (a job with a prompt id is released with no question about its files, it is the operator's discard), and the warning says the files were ignored; (5) not listed, no files = released without ceremony. This also frees a QUEUED/PENDING job whose prompt ComfyUI forgot (e.g. after a restart). The UI shows `warning` after `message`.
- The 409 dialog of "Nạp Render Vào Queue ComfyUI": when the refusal carries `can_force` (same configuration already journaled, `RECOVERY_REQUIRED` job, an old prompt still in ComfyUI's queue, state duplicate) the page asks "Chạy lại (force)?" and resends with `force: true`. `can_force` is false for an unreconciled intent: wait or release it.
- Force and a still-queued old prompt: without `force`, a dispatch of a DIFFERENT configuration is refused (409) while another STARTED prompt of that shot is still in ComfyUI's `/queue`. With `force`, Studio first cancels the old prompt (`POST /queue {"delete":[id]}` if pending; if running it reads `/queue` AGAIN immediately before `POST /interrupt` and interrupts only when that same prompt is still the running one, because `/interrupt` stops whatever runs at that moment), then posts the new one. The replaced job is closed `SUPERSEDED` only when ComfyUI no longer lists it; until then it stays open with state status `SUPERSEDED_PENDING` (it does not block dispatch) and `scan_outputs` closes it once the queue has let go. A parked `RECOVERY_REQUIRED` job replaced by force is closed `SUPERSEDED` the same way.
- `scan_outputs` also learns the outcome of parked jobs (`/history/<prompt_id>`): a finished one gets its final status and a `terminal` record, freeing the slot. Its `files` list now includes every parked job (`parked: true`, `status`, `prompt_id`, `job_id`; `prompt_id` null for a recovery job). It reports status only: it does not import the clips of a parked job. State changes are saved at the end of the scan.
- Intent without a started record (crash or lost answer): `dispatch` / `start_render` reconcile it first. ComfyUI: `/queue`, then the WHOLE `/history` (no `max_items` window), then the job's output folder. Found = started. Reachable and absent from a non-empty history with no output folder = `ABANDONED` (re-dispatch allowed). Absent but output files exist, or history is empty (ComfyUI restarted or cleared) = a started record with no prompt id, i.e. `RECOVERY_REQUIRED`, never auto-abandoned. ComfyUI unreachable = 409. An open intent younger than `intent_grace` (120 s; env `JENNIEJOY_INTENT_GRACE_SECONDS`) is treated as in flight (409) unless ComfyUI already lists it, so a second engine instance cannot abandon and re-POST it.
- Render intents use the process table (PowerShell `Get-CimInstance`, 30 s timeout). A process counts when ITS OWN command line holds `...\jobs\<job_id>` followed by a path separator, end of line, a quote or a space (a bare directory argument matches; `<job_id>.json` and longer names do not). Limit: a child process that does not carry the job directory in its own command line (for example an ffmpeg started by node) is not found; the parent is the anchor. Found = started, absent after the grace = `ABANDONED`, unreadable = 409. The lookup runs in `Studio.action` BEFORE the lock for the three render routes and is reused under the lock.
- Remaining limit: ComfyUI keeps its history in memory. A prompt that finished, whose history was wiped and whose outputs were deleted or never written under the job folder cannot be told from one that never ran, so it is `ABANDONED` when the history is non-empty. Jobs submitted before this scheme have no job-specific output folder and no `studio_job_id`.
- `dispatch` evaluates its guard (reconcile, journal duplicates, `RECOVERY_REQUIRED`, still-queued old prompt, state duplicates) at the top AND again under the lock right before the submit. A job found live at startup is `RECOVERY_REQUIRED` for finishing jobs; `/api/jobs/recover` re-verifies those (a journaled COMPLETED too, because publishing lives in the state file).
- 409 on `Studio.save`: (1) the rejected in-memory copy is written to `studio-state.conflict-<UTC>.json` (never overwritten; your other edits are NOT adopted automatically), (2) the file is reloaded in place, (3) the journal re-attaches jobs as above. After an external effect (prompt queued, process started) `dispatch` / `start_render` save through `_save_merged`: one retry after the first 409; a second 409 is NOT raised, the call succeeds with a `warning` ("tải lại trang") because the job is already in the journal. The UI shows `warning` after `message`.
- Finishing threads keep a handle (`Studio._finish_threads`) and close `render.log` BEFORE writing the terminal record; tests join the thread before deleting the temp tree.
